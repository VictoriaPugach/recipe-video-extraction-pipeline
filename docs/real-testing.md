# План реальной проверки извлечения

Автоматические тесты (`make test`) подменяют внешние вызовы и проверяют поведение, контракт и границы, но не доказывают качество распознавания на настоящих видео. Этот документ — протокол недостающей проверки: реальные URL, реальные модели, три типа входа. Пункты соответствуют позициям 2 и 10 в [src/TODO.md](../src/TODO.md) и рубрике приёмки [evaluation.md](evaluation.md).

## Набор видео: три типа входа

Источники информации в видео — речь (STT) и надписи на экране (OCR). Набор приёмки покрывает все три сочетания:

| Тип | Речь | Надписи | Что проверяет |
| --- | --- | --- | --- |
| Только текст | нет (музыка или тишина) | да | OCR-путь; STT не должен выдумывать текст из музыки |
| Только аудио | да | нет | STT-путь; пустой OCR не должен ломать сборку рецепта |
| Сочетание | да | да | слияние двух источников в `fusion.py` без дублирования и противоречий |

Основной набор и доступные результаты:

| Локальный файл | Тип | Длительность | Upload и сравнение |
| --- | --- | ---: | --- |
| `shakshuka.mp4` | только аудио | 24,590 с | JSON приложен; 40/40 = 100,0%, PASS |
| `plov.mp4` | речь + надписи | 100,300 с | последний вывод 51/60 = 85,0%, PASS; новый JSON ещё не приложен |
| `tomatoChickpea.mp4` | только текст | 72,075 с | JSON приложен; 31/32 = 96,8%, PASS |

Для `tomatoChickpea.mp4` рецепт дан в надписях, звук — музыка; ожидается пустая
или почти пустая расшифровка и сборка рецепта из OCR. Источники и ограничения
доказательств перечислены в [provenance.md](../data/input_videos/provenance.md).
`chocolateCake.mp4` и `butterChicken.mp4` — дополнительные эксперименты, а не
замена основных случаев. Все пять MP4 включены в ветку; их размещение в наборе
согласовано с ревьюерами.

## Подготовка набора

1. Положи MP4 в `data/input_videos/`, скопируй `manifest.example.json` в `manifest.json` и заполни источник, права, длительность и путь к разметке (правила — в [data/input_videos/README.md](../data/input_videos/README.md)).
2. Вручную выпиши эталоны в `data/expected_outputs/<имя>.json` по содержимому видео — только подтверждённые роликом сведения, неизвестное — `null`. Синтетические `pasta.json`, `omelette.json`, `salad.json` заменить или удалить из набора.
3. Проверь эталоны контрактом:

```bash
.venv/bin/python -m fropti_core_contracts data/expected_outputs/*.json
.venv/bin/python scripts/compare_gold.py --validate-only data/expected_outputs/*.json
```

4. Зафиксируй нормализацию **до** прогонов: регистр и пробелы, единицы, обработка неизвестных значений. Рекомендуемый пресет для `compare_gold.py`: `--exclude /source --absent-equals-null --skip-notes --skip-instructions`; выбор запиши в `data/input_videos/provenance.md` вместе с автором видео, датой получения и автором разметки.

   Флаги `--skip-notes` и `--skip-instructions` выводят из количественной метрики единственные поля свободной формы — `note` ингредиентов и содержимое текстов шагов. Произвольные уточнения видео («без горки», «через сито») и перефразированные инструкции нормированной записи не имеют; точное совпадение строк наказывало бы формулировку, а не ошибку извлечения. Существование каждого шага при этом сохраняется в метрике: пропущенный или лишний шаг остаётся расхождением, а `--absent-equals-null` не засчитывает nullable-поля полностью отсутствующего элемента списка. Качество шагов это не отменяет: каждый прогон дополнительно оценивается вручную против видео, вердикт фиксируется в `provenance.md` («Шаги: N/N по существу верны, формулировки различаются; отклонения: …»).

   Ингредиенты сравнитель сопоставляет по имени, а не по позиции списка: пропущенный или лишний ингредиент стоит ровно своих полей и не сдвигает пары остальных. Измеряемая часть прежняя: `quantity.value`, `quantity.unit`, длительности шагов, `title`, `servings`; допустимость единиц (`unit` в пределах enum 1.0.0) страхует валидация контрактом. Нормализация фиксируется до прогонов, применяется ко всем видео набора одинаково и после прогона не меняется.

## Протокол прогона (для каждого видео)

Для каждого видео выполнить оба способа ввода и сохранить артефакты:

```bash
# 1. CLI, локальный файл
.venv/bin/python -m src.main --file data/input_videos/tomatoChickpea.mp4 \
  > runs/tomatoChickpea.file.json

# 2. API, локальный файл (обёртка проверяет файл до curl — без неё пропажа файла выглядит как «curl: (26)»)
make run
scripts/upload.sh data/input_videos/tomatoChickpea.mp4 \
  > runs/tomatoChickpea.upload.json

# 3. URL (если видео доступно на согласованной платформе)
curl -s -X POST http://localhost:8000/extract \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://..."}' \
  > runs/tomatoChickpea.url.json

# 4. Сравнение с эталоном (пресет п. 4)
.venv/bin/python scripts/compare_gold.py --exclude /source --absent-equals-null \
  --skip-notes --skip-instructions \
  data/expected_outputs/tomatoChickpea.json runs/tomatoChickpea.file.json
```

Для каждого прогона зафиксировать: дату, команду, снимок настроек (без `LLM_API_KEY`), версии моделей (faster-whisper/пакетов — `pip freeze`), результат `compare_gold.py` (числитель, знаменатель, процент, список расхождений). Промежуточные артефакты — расшифровка речи и текст с экрана — приложить в обезличенном виде: по ним видно, из какого источника пришёл каждый факт рецепта. Их сохраняет переменная `DEBUG_ARTIFACTS_DIR`: каждый запуск пишет `transcript.txt` и `screen_text.txt` в свой подкаталог `run-*` (в `docker-compose.full.yml` том `./runs/debug:/runs/debug` уже подключён). Куда складывать: папку `runs/` в корне (в репозиторий коммитить только обезличенные артефакты; `runs/debug/` игнорируется Git).

## Проверка URL отдельно

Для URL достаточно одной заранее согласованной платформы. Перед прогоном:

- в контейнере `node --version` должен показывать 22.x (`docker compose -f docker-compose.full.yml build api` после обновления образа);
- платформа должна входить в `ALLOWED_URL_HOSTS` (по умолчанию — домены YouTube);
- видео — в пределах 180 с и 100 МиБ (`MAX_DOWNLOAD_BYTES`);
- URL-запуск использует `EGRESS_PROXY_URL`; в Compose API находится только на `internal`-сети, поэтому обход прокси не даёт прямого интернет-доступа.

Перед URL-демонстрацией выполнить `bash scripts/test_egress.sh` на машине с Docker. Скрипт отдельно проверяет разрешённый публичный HTTPS, запрет loopback/link-local, редирект на loopback, запрет небезопасного порта и невозможность прямого соединения с `--noproxy '*'`. Это сетевая интеграционная проверка; `make test` её не заменяет.

Ответ «Sign in to confirm you're not a bot» — ограничение со стороны YouTube, а не сам по себе дефект кода. При законном использовании можно настроить собственный Netscape-файл через `YTDLP_COOKIES_FILE` и локальное монтирование `./cookies.txt:/cookies.txt:ro`; cookies являются учётными данными, остаются вне Git и не печатаются в логах. Обход ограничений доступа в проект не встраивается ([SECURITY.md](../SECURITY.md)). Неудачные попытки фиксировать с причиной — они входят в отчёт как ограничение платформы, а не как успешное извлечение.

## Критерии готовности проверки

- [ ] Видео набора покрывают все три типа входа; у каждого есть источник, права и ручной эталон.
- [ ] Каждый эталон проходит `fropti_core_contracts` и `compare_gold.py --validate-only`.
- [ ] Для каждого видео: `POST /extract/upload` и CLI вернули `200`/код `0` с валидным `Recipe`; для согласованной платформы — `POST /extract` по URL.
- [ ] 100% успешных ответов проходят общий `Recipe`; совпадение с эталоном ≥80% путей по метрике [evaluation.md](evaluation.md#как-считать-совпадение-полей) для каждого видео.
- [ ] Приложены: команды, обезличенные промежуточные артефакты, отчёты `compare_gold.py`, демонстрационный ролик до 4 минут по [PR-шаблону](../.github/pull_request_template.md).

Результат набора демонстрирует качество на этих видео и не обобщается на все видео и платформы.
