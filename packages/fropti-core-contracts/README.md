# fropti-core-contracts 1.0.0

Единый контракт `Recipe` для модулей трёх команд Fropti. Источник истины — модели этого пакета. Контракт применяется к рецептам из ссылок, загруженных видео и ручного ввода. Он не зависит от FastAPI, STT, OCR или LLM.

Пакет находится в этом репозитории. Публикация в PyPI не выполнялась. Для локальной установки из корня репозитория:

```bash
python -m pip install ./packages/fropti-core-contracts
```

Для передачи другим командам можно собрать wheel и устанавливать один и тот же артефакт:

```bash
python -m pip wheel --no-deps ./packages/fropti-core-contracts --wheel-dir dist
python -m pip install dist/fropti_core_contracts-1.0.0-py3-none-any.whl
```

## Использование

```python
from fropti_core_contracts.models import Recipe

recipe = Recipe.model_validate({
    "schema_version": "1.0.0",
    "title": "Омлет",
    "servings": None,
    "ingredients": [
        {"name": "Яйцо", "quantity": {"value": 2, "unit": "pcs"}},
        {"name": "Соль", "quantity": None, "note": "По вкусу"},
    ],
    "steps": [{"instruction": "Взбить яйца с солью и обжарить."}],
    "source": {"type": "manual"},
})
print(recipe.model_dump_json())
```

Готовый JSON можно проверить без написания кода:

```bash
python -m fropti_core_contracts recipe.json
```

Для интеграции в Python пакет экспортирует `validate_recipe(...)` и `validate_recipe_json(...)`. Оба используют единственную модель `Recipe`; отдельных валидаторов с расходящимися правилами для планировщика и списка покупок нет.

`schema_version`, `title`, `servings`, `ingredients`, `steps` и `source` обязательны. Неизвестное число порций передаётся как `null`. У каждого ингредиента обязательны `name` и `quantity`; неизвестное количество передаётся как `null`. Пустые списки ингредиентов и шагов, строки только из пробелов и неизвестные поля отклоняются. Ввод не очищается скрытым удалением пробелов.

Количество — положительное конечное число и единица из `g`, `kg`, `ml`, `l`, `pcs`, `tsp`, `tbsp`, `pinch`. Числа в строках и логические значения недопустимы. `servings`, `total_time_minutes` и `duration_seconds` — положительные целые числа либо `null`; для необязательных времён отсутствие поля также допустимо. Числовое значение `2.0` принимается как целое `2`, а дробное `2.5` отклоняется. Количества и времена нельзя додумывать по умолчанию.

Источник задаётся одним из объектов:

- `{"type": "url", "url": "https://example.com/video"}` — публичная ссылка HTTP/HTTPS.
- `{"type": "upload"}` — загруженное видео, без локального пути или имени файла.
- `{"type": "manual"}` — рецепт, созданный вручную.

Проверка URL в контракте проверяет формат HTTP/HTTPS, наличие хоста и отсутствие пробельных символов. Проверка разрешённых хостов, запрет доступа к внутренней сети и ограничения скачивания относятся к сервису, который получает видео.

## JSON Schema и мобильное приложение

[schemas/recipe-1.0.0.schema.json](schemas/recipe-1.0.0.schema.json) — генерируемый JSON Schema Draft 2020-12. Он предназначен для валидации JSON и реализации DTO в Flutter/KMP без зависимости от Python. Целочисленные поля принимают числовые значения без дробной части, включая `2.0`, и сериализуются как целые числа.

Из корня репозитория после установки пакета:

```bash
python -m fropti_core_contracts.schema --output packages/fropti-core-contracts/schemas/recipe-1.0.0.schema.json
python -m fropti_core_contracts.schema --check packages/fropti-core-contracts/schemas/recipe-1.0.0.schema.json
```

Без аргументов команда печатает схему в stdout. `--check` возвращает ненулевой код при отличии или отсутствии файла. Схема входит в wheel как data file в `share/fropti-core-contracts/schemas`.

## Правила совместимости

Все три команды используют версию `1.0.0` и проверяют входящий `schema_version`. Формат одного рецепта одинаков в API, JSON-примерах и хранилище; идентификатор записи и метаданные хранения принадлежат внешнему объекту сервиса.

Модуль извлечения производит `Recipe`, cooking planner / batch cooking читает `steps` и `servings`, а shopping list читает `ingredients` и `servings`. Граф задач, кухонные ресурсы, складские остатки и результат агрегации являются отдельными контрактами потребителей и не добавляются в `Recipe`.

Изменения полей, типов, обязательности и правил валидации требуют согласованного нового контракта и обновления схемы, примеров и проверок потребителей в одном PR. Из-за запрета неизвестных полей даже добавление необязательного поля требует миграции потребителей; нельзя молча менять существующий `1.0.0`. Исправления документации без изменения принимаемых JSON не меняют контракт. Аллергены, пищевая ценность и привязка к каталогу не выводятся из рецепта автоматически и не входят в эту версию.
