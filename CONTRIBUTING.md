# Как работать над модулем

Работа проходит через Pull Request. Реализовывать один проверяемый шаг за раз; изменения общего контракта вносить в `packages/fropti-core-contracts/` через PR с ревью Виктории Пугач.

## Первый запуск

```bash
cp .env.example .env
make install
make test
make run
```

Прочитать [README](README.md), [архитектуру](docs/architecture.md), [схему](docs/data_schema.md) и [план реализации](src/TODO.md). Текущий `501` — ожидаемое поведение заглушки. Не подменять извлечение заранее заготовленным рецептом.

## Ветки и PR

1. Создать ветку `feature/<краткая-задача>` или `fix/<краткая-задача>` от актуальной основной ветки.
2. Описать ожидаемое поведение и границы изменения.
3. Реализовать изменение и добавить тесты публичного поведения в принятом стиле pytest.
4. Выполнить `make test`. Для изменения API отдельно проверить затронутый сценарий через `/docs` или Postman.
5. Открыть PR по [шаблону](.github/pull_request_template.md), приложить команды, результаты и известные ограничения. Указать невыполненные проверки и причины.

В PR описать новые зависимости, переменные окружения и изменения контракта; приложить разрешённые исходные данные для воспроизведения и JSON-результат. Пример из заглушки или синтетического набора явно обозначить как таковой. Для итоговой сдачи приложить демонстрационный ролик до четырёх минут с таймкодами: постановка задачи, демонстрация работы, доказательства успешности и заключение; отдельно перечислить сделанное и невыполненное.

Отдельно отметить, относится изменение к обязательному MVP или к бонусу. Бонус не должен расширять объём PR, пока затронутый обязательный сценарий и его тесты не завершены.

## Изменения контракта

Использовать `Recipe` 1.0.0 из общего пакета; не создавать собственную модель с тем же назначением. После изменения модели сгенерировать JSON Schema, обновить версию по [правилам совместимости](docs/data_schema.md#версии-и-изменения), примеры и тесты. В PR описать влияние на все три команды и порядок миграции. Проверить совпадение модели и схемы:

```bash
.venv/bin/python -m fropti_core_contracts.schema --check packages/fropti-core-contracts/schemas/recipe-1.0.0.schema.json
```

Для новой версии использовать соответствующее имя схемы. Опубликованные версии не перезаписывать.

## Ревью

Ревьюеры — **Виктория Пугач** и **Люба Новохацкая**. Виктория отвечает за контракты; Люба — за безопасность; обе проверяют пайплайн и тесты. Изменение профильной области направлять соответствующему ревьюеру.

Для объединения PR получить минимум **один approve** от любого из двух ревьюеров. Для спорного PR — **два approve, по одному от каждого**. Спорным считать PR с неразрешённым разногласием ревьюеров по поведению, контракту, безопасности или результатам проверки. Сначала зафиксировать согласованное решение, затем получить оба approve. Все блокирующие замечания закрыть до объединения.

Эти правила описывают процесс команды; настройка защиты ветки в GitHub здесь не подтверждена. Объединение промежуточного PR не означает готовности всего модуля. Полная рубрика, ответственность за проверки и правило совместного пересмотра оценок приведены в [evaluation.md](docs/evaluation.md).

## Проверки и данные

Тесты API с подменой внешних вызовов подтверждают обработку запроса, но не качество STT/OCR/LLM. Для оценки качества использовать реальные видео и ручную разметку. Требования к данным описаны в [data/input_videos](data/input_videos/README.md).

Обычный CI должен проходить без API-ключей, оплачиваемых LLM-запросов и скачивания моделей. Реальные внешние сервисы проверять отдельно и документировать результаты. Не создавать тесты приватных методов; проверять публичное поведение модулей.

Не добавлять в коммиты `.env`, API-ключи, cookies, персональные данные и файлы без прав на использование. Новые зависимости фиксировать в `requirements.txt`; требования тяжёлых моделей к ресурсам объяснять в PR. Об уязвимостях сообщать по [SECURITY.md](SECURITY.md).
