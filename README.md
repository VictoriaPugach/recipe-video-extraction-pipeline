Модуль извлечения рецептов из коротких видео для **Fropti — планировщика домашнего питания**. Целевой сценарий: человек загружает видео с устройства или отправляет ссылку на YouTube Shorts, Reels или RuTube, сервис объединяет речь, надписи и кадры в структурированный рецепт, а приложение использует его для планирования питания. Поддержку каждой платформы студент должен реализовать и проверить отдельно.

## О проекте

Fropti помогает ответить на три связанных вопроса: **что приготовить, когда готовить и какие продукты понадобятся**. В продуктовом замысле приложение учитывает продукты дома, предпочтения, ограничения и график готовки. Видео с интересным блюдом становится частью этого сценария: рецепт нужно не просто сохранить, а превратить в данные, которые можно использовать в меню и списке покупок.

Исходные материалы питча и макеты целевого продукта перечислены в [инструкции к слайдам](docs/slides/README.md). Они объясняют контекст задачи, но не подтверждают готовность показанных функций или интеграций.

**Задача модуля:** преобразовать видео в валидный `Recipe` для передачи в приложение. От результата зависят ингредиенты в списке покупок, расчет порций и инструкция для человека, который будет готовить.

1. **Проблема.** Пустой холодильник, экран доставки и уставший человек. Текст: «Хочу домашнее, но нет сил выбирать».

3. **Модуль.** Видео → аудио и кадры → STT/OCR → LLM → валидация → JSON Recipe. Текст: «Этот модуль превращает видео в готовый рецепт для плана».

## Что уже есть и что предстоит сделать

| Сейчас в каркасе | Задача студента |
| --- | --- |
| FastAPI, CLI, Docker и команды запуска | Скачать видео и проверить его длительность |
| Прием видеофайла и проверка формата входного URL | Реализовать извлечение кадров, STT и OCR |
| Единый пакет `fropti-core-contracts` 1.0.0 и JSON Schema | Объединить сигналы через LLM и валидировать результат |
| Тесты границ API и синтетические JSON | Добавить реальные видео и проверить качество извлечения |
| Документы, пример клиента и коллекция Postman | Проверить интеграцию других модулей по единой схеме |

**Реальный пайплайн пока не реализован.** Корректный URL и непустой файл в пределах лимита приводят к `501 pipeline_not_implemented`. Каркас принимает файлы, но не скачивает видео по ссылке и не вызывает модели. Проверка лимита в 180 секунд предусмотрена в пайплайне, но начинает работать с реальным видео после реализации определения длительности. Проходящие тесты каркаса не доказывают качество извлечения.

## Quick Start

Нужны Git и Docker с Compose. Для локального запуска — Python 3.10+.

```bash
git clone https://github.com/VictoriaPugach/recipe-video-extraction-pipeline.git
cd recipe-video-extraction-pipeline
cp .env.example .env
docker compose up --build
```

Альтернатива без Docker, после клонирования и создания `.env`:

```bash
make install
make run
```

Открыть [Swagger UI](http://localhost:8000/docs). Для отправки видео: **POST /extract/upload → Try it out → выбрать файл → Execute**. Пока распознавание не реализовано, ожидается `501`.

Проверка доступности:

```bash
curl http://localhost:8000/health
```

Ответ:

```json
{"status": "ok", "contract_version": "1.0.0"}
```

Это проверка доступности HTTP-сервиса, а не готовности распознавания. База данных для этого stateless MVP не нужна. Docker-образ включает `ffmpeg`; для локальной обработки медиа его необходимо установить отдельно. Whisper, OCR и клиент LLM пока не выбраны и не включены в обязательные зависимости каркаса.

## Пример запроса и ответа

**Видео с устройства** отправляется как файл:

```bash
curl -i -X POST http://localhost:8000/extract/upload \
  -F 'file=@data/input_videos/pasta.mp4'
```

`pasta.mp4` — имя будущего тестового видео. Для запуска добавить файл или заменить путь на существующий. В репозитории MP4 пока нет. Файл должен быть непустым и не больше **100 МиБ**. Проверка формата медиа и реальной длительности входит в задачи реализации пайплайна.

**Видео по ссылке** отправляется как JSON:

```bash
curl -i -X POST http://localhost:8000/extract \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://www.youtube.com/shorts/EXAMPLE_ID"}'
```

`EXAMPLE_ID` — плейсхолдер, а не тестовое видео. Текущий ответ каркаса — `501 Not Implemented`:

```json
{"detail": {"code": "pipeline_not_implemented", "message": "..."}}
```

Ниже **синтетический пример будущего `200 OK` по общему контракту 1.0.0**, а не результат обработки этой ссылки:

```json
{
  "schema_version": "1.0.0",
  "title": "Омлет",
  "servings": 1,
  "ingredients": [
    {"name": "Яйца", "quantity": {"value": 2, "unit": "pcs"}, "note": null},
    {"name": "Соль", "quantity": null, "note": "По вкусу"}
  ],
  "steps": [
    {"instruction": "Взбейте яйца с солью.", "duration_seconds": null},
    {"instruction": "Приготовьте омлет на сковороде.", "duration_seconds": null}
  ],
  "source": {"type": "url", "url": "https://www.youtube.com/shorts/EXAMPLE_ID"},
  "total_time_minutes": null
}
```

Оба способа используют один пайплайн и один `Recipe`. Для локального или загруженного файла источник — `"source": {"type": "upload"}`; фиктивная ссылка, имя файла и серверный путь в ответ не включаются.

Лимит — **180 секунд включительно**. Видео длиннее лимита должно давать `400 video_too_long`; неверный JSON или URL, отсутствие файла — `422`; пустой файл — `400 empty_file`, файл больше 100 МиБ — `413 file_too_large`. Полный контракт: [API reference](docs/api_reference.md).

CLI использует тот же пайплайн:

```bash
.venv/bin/python -m src.main 'https://www.youtube.com/shorts/EXAMPLE_ID'
.venv/bin/python -m src.main --file data/input_videos/pasta.mp4
```

Выбрать один источник: URL или `--file`. CLI читает локальный файл напрямую, без HTTP-загрузки. Для обращения к запущенному API есть клиент:

```bash
.venv/bin/python examples/example_client.py --file data/input_videos/pasta.mp4
```

## Контракты данных и мобильная интеграция

Python работает **на сервере**. Мобильное приложение на Flutter или KMP — выбор еще не сделан — обращается к FastAPI по REST. Python, Whisper, OCR и LLM не запускаются нативно на телефоне. Схема API доступна в `/openapi.json`.

Единый источник модели — [пакет `fropti-core-contracts` 1.0.0](packages/fropti-core-contracts/) в этом репозитории. `make install` устанавливает его вместе с сервисом. Все Python-модули используют `from fropti_core_contracts.models import Recipe`; отдельной локальной схемы нет.

Для других команд доступны устанавливаемый Python-пакет и [JSON Schema 1.0.0](packages/fropti-core-contracts/schemas/recipe-1.0.0.schema.json). Мобильный клиент использует ту же JSON-структуру через REST. Поля, неизвестные значения, единицы, подключение из другого репозитория и правила версий описаны в [схеме данных](docs/data_schema.md). Публикация пакета в PyPI или отдельном удалённом репозитории пока не выполнена.

## С чего начать

1. Запустить сервис, открыть `/docs` и получить ожидаемый `501`.
2. Выполнить `make test`, затем изучить [архитектуру](docs/architecture.md).
3. Изучить общий `Recipe` 1.0.0 и подготовить три доступных для использования видео. Пока в репозитории только синтетические JSON, а не результаты распознавания.
4. Реализовать определение длительности в `src/downloader.py`. Первым рабочим сценарием проверить отказ для видео длиннее 180 секунд.
5. Собрать сквозной сценарий «локальное видео → Recipe», затем добавить остальные источники сигналов и платформы. Этапы реализации перечислены в [src/TODO.md](src/TODO.md).

## Объём задания: MVP и бонусы

Обязательный MVP укладывается в лимит **10–12 часов** при готовых доступах и трёх коротких разрешённых видео:

- обработать локальный MP4 и URL хотя бы одной согласованной платформы одним пайплайном;
- проверить длительность до тяжёлой обработки, выполнить STT, выбор кадров, OCR и объединение через LLM;
- вернуть только валидный `Recipe` 1.0.0, явно сохраняя неизвестные значения;
- покрыть публичное поведение тестами без внешних ключей и провести отдельный реальный прогон на трёх видео;
- зафиксировать команды, версии моделей, результаты и ограничения.

Бонусы выполняются только после MVP и не входят в оценку времени: дополнительные видеоплатформы, асинхронная очередь, GPU-оптимизация, UI, база данных и автоматическая публикация общего пакета. Их отсутствие не следует маскировать общими заявлениями о поддержке.

## Ожидаемое время

| Этап | Оценка |
| --- | --- |
| Изучение проекта и контракта | 1 ч |
| Скачивание и проверка длительности | 1–2 ч |
| STT и OCR | 3–4 ч |
| Объединение через LLM | 2 ч |
| Тесты, реальный прогон и документация | 3 ч |

Итого — **10–12 часов**. Это лимит обязательного MVP для разработчика, знакомого с Python, при готовых видео, контракте и доступах. Ожидание согласований, загрузка моделей и бонусы в оценку не входят; если обязательный сценарий не помещается в лимит, сначала сокращается бонусный охват платформ, а не проверки контракта, безопасности или тесты.
